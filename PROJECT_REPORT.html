1. Problem Selection & Real-World Relevance

In multi-specialty healthcare environments, patient medical profiles are dynamic, semi-structured, and subject to evolving regulatory requirements. Relational Database Management Systems (RDBMS) impose rigid schema definitions that struggle with multi-disciplinary clinical visits, high-frequency vitals telemetry, and variable diagnostic test results.

Retrieving a complete clinical encounter in SQL requires joining 5 to 7 separate tables (patients, encounters, vitals, prescriptions, lab_orders, billing), resulting in noticeable latency and high CPU usage under concurrent workloads.

Core NoSQL Advantage: MongoDB's document model allows natural embedding of vitals logs and prescriptions inside individual encounter records. This delivers single I/O fetch speeds ($O(1)$) and document-level atomic writes without expensive relational table locks.

2. Database & Document Design

The MediPulse system organizes clinical records into four primary collections: patients, doctors, encounters, and appointments.

Embedding vs. Referencing Rationale

Relationship Design Strategy Architectural Decision Rationale
Encounter $\rightarrow$ Vitals & Prescriptions Embedded Arrays 1:Few Cardinality & Bounded Growth: A patient visit typically has 2–20 vitals and 1–6 medications. Embedding eliminates joins, keeps documents under 4KB (well below MongoDB's 16MB limit), and ensures atomic updates.
Patient $\rightarrow$ Encounters Referenced by patient_id 1:Many Unbounded Growth: A patient may visit the hospital hundreds of times over their lifetime. Embedding all visits in a single patient document would lead to document bloating and exceed the 16MB limit.
Doctor $\rightarrow$ Encounters Referenced by doctor_id Independent Entity: Doctors exist independently as hospital staff and consult thousands of patients over years.

Indexing Strategy

Collection Index Specification Type Operational Benefit
patients {"patient_id": 1} Unique Guarantees unique primary identification; $O(1)$ point lookups
patients {"blood_group": 1} Single Field Rapid emergency blood donor matching
patients {"name": "text", "medical_profile.chronic_conditions": "text"} Text Index Inverted index for full-text search across clinical records
encounters {"department": 1, "admission_date": -1} Compound Optimizes chronological departmental admission queries
encounters {"vitals_log.timestamp": -1} Multikey Fast temporal querying of nested telemetry readings

3. MongoDB Schema Validation ($jsonSchema)

MediPulse applies strict collection-level validation rules inside the MongoDB engine using $jsonSchema with validationLevel: "strict" and validationAction: "error". 

{
  "$jsonSchema": {
    "bsonType": "object",
    "required": ["patient_id", "name", "gender", "blood_group", "dob", "contact"],
    "properties": {
      "patient_id": { "bsonType": "string", "pattern": "^PAT-[0-9]{4,}$" },
      "blood_group": { "enum": ["A+", "A-", "B+", "B-", "AB+", "AB-", "O+", "O-"] },
      "contact": {
        "bsonType": "object",
        "required": ["phone", "email"],
        "properties": {
          "phone": { "bsonType": "string", "pattern": "^\\+?[0-9\\s\\-]{10,15}$" }
        }
      }
    }
  }
}
Negative Validation Proof: Inserting a document with an invalid blood group ("Z+") or an invalid phone number was blocked by the MongoDB engine with WriteError: Document failed validation against collection $jsonSchema (Code: 121).

4. CRUD Operations Catalog

  • Create: insert_one for patient registration; insert_many for bulk appointments ingestion.
  • Read: Equality queries with projection, compound filters with $and and $or, text search with $textScore ranking, and nested array queries with $elemMatch.
  • Update: $set for demographic updates, $push for appending new vital readings, $addToSet for recording unique allergies, and atomic $set + $inc for encounter discharge and billing updates.
  • Delete: delete_one for appointment cancellation, delete_many for purging cancelled logs.
